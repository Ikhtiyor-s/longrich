## 2026-10-20 — `offers_summary` on `GET /v1/catalog/products` (list + detail) is permanently hardcoded to zero, never wired to real `seller_offers` data

**Found by:** architect pass, `docs/architecture/ui-contract-g7-buyer-catalog.md` preparation.

**What:** `apps/api/src/modules/catalog/variants/variants.mapper.ts`'s `emptyOffersSummary()` (`{ active_offer_count: 0, lowest_price_minor: null, currency: null }`) is called unconditionally by both `apps/api/src/modules/catalog/products/products.mapper.ts` (`toProductListItemPayload`, `toProductDetailPayload`) and `variants.mapper.ts`'s own `toVariantPayload`. `docs/architecture/api-contract-g2.md` states explicitly: *"`offers_summary` ships with this exact shape from day one (zero-valued until `T-G2-5` lands, never a `NOT_AVAILABLE` placeholder string) — `T-G2-5` never changes this shape, only starts populating it with live aggregates."* Grep across `apps/api/src` confirms `T-G2-5` (seller-offers CRUD, confirmed shipped — `seller-offers.service.ts`/`offers.mapper.ts`/`public-offers.controller.ts` all exist and are real) never went back and patched `products.mapper.ts`/`variants.mapper.ts` to replace `emptyOffersSummary()` with a real `COUNT`/`MIN` query over `seller_offers WHERE status='ACTIVE' AND seller.status='ACTIVE'`. Every call to `GET /v1/catalog/products`, `GET /v1/catalog/products/{id}`, and every variant's embedded `offers_summary` today returns `active_offer_count: 0, lowest_price_minor: null` **regardless of how many real ACTIVE offers actually exist** for that product/variant.

**Why it matters:** The only endpoint that returns real per-seller offer data is `GET /v1/catalog/variants/{id}/offers` (`public-offers.controller.ts` → `toPublicOfferPayload`), which is correct and live. Any frontend code (or future backend consumer) that trusts `offers_summary.lowest_price_minor`/`active_offer_count` directly from the products list/detail endpoints will always see "no price / no offers," even when real offers exist. `apps/web-buyer/app/page.tsx`'s existing (soon-to-be-rebuilt) `getLowestPrice()` already works around this correctly today by walking `variants[] → GET /v1/catalog/variants/{id}/offers` per product instead of reading `offers_summary` — this is **not a coincidence**, it's the only path that actually returns live data, and `docs/architecture/ui-contract-g7-buyer-catalog.md` freezes the same walk as the Home/Category page data-fetching contract specifically because of this gap.

**Not fixed here.** No ticket in `tickets/g2/` or `tickets/g7-buyer-web-catalog/` tests or requires `offers_summary` to be real — fixing it would mean adding a live aggregate query to `products.service.ts`'s list/detail paths, which is backend-dev work, out of scope for the UI-contract-freeze pass that found it. Flagged so a future ticket (likely a small addition riding along with whichever milestone next touches `catalog/products`) closes this instead of someone re-discovering it mid-implementation and guessing a fix inline.

**Severity:** MEDIUM — no data-integrity risk (the field is honestly zero/null, never fabricated), but a real functionality gap: product list/detail responses cannot answer "does this product have an active offer / what's its lowest price" today without the N+1 variants→offers walk.
